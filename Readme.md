Live website: https://sdtgsoi.github.io/ds991_web/

This program is aimed to rebuild a scientific calculator with web page, which simulates the calculator fx991 CN X (however, this project is not related to any company/manufacturer)

This program is fully generated by AI tools, and is still under development

# Development

The app remains a self-contained HTML page with no runtime dependencies.
Use Node.js **22+** for development tools; no package installation is required.
Open `ds991.html` directly, or serve the repository with a static HTTP server.

- Edit the page shell, CSS, state, evaluator and mode handlers in `ds991.html`.
- Edit numerical algorithms in `src/math-core.js`, editing behavior in
  `src/expression-editor.js`, expression layout in `src/expression-renderer.js`,
  LCD screens in `src/screen-renderer.js`, and menu data/navigation in `src/menus.js`.
- Blocks between `BEGIN GENERATED ...` / `END GENERATED ...` in the HTML are
  generated from those files; edit the source files instead of these blocks.
- Run `./sync.sh` after changing a source. It embeds the sources in `ds991.html`,
  validates the script, then copies the page to `index.html`. There is no bundler
  and no external JavaScript file to load at runtime.

`index.html` is a byte-identical copy that exists purely because GitHub Pages
serves `index.html` from the repository root. Regenerate it before committing or
pushing:

```bash
./sync.sh            # ds991.html -> index.html, with validation
./sync.sh --check    # report whether the two files agree (exit 1 if not)
```

The script refuses to copy a page that is empty, is missing its main elements, or
has a JavaScript syntax error, so a half-saved file can never reach the
published copy.

## Publishing changes

```bash
# 1. edit ds991.html
./sync.sh            # 2. regenerate index.html
node tools/run_tests.js   # 3. run the suites
node tools/sync_test.js
node tools/prepush_test.js
node tools/browser_lifecycle_test.js
node tools/browser_test.js # Chrome/Chromium required
git add -A && git commit -m "..."
git push
```

Or run the checks as one command before pushing:

```bash
./tools/prepush.sh            # sync check + suites + "is the remote ahead?"
./tools/prepush.sh --no-test  # skip the suites
```

`prepush.sh` exits non-zero if any required check fails: the
embedded sources and both HTML files agree, the suites pass, the
working tree is clean, and the configured upstream has no commits you are missing.
Missing Node, upstream, failed fetch or failed comparison makes the check fail.
`--no-test` is an explicit partial check and is reported as such. A remote ahead
of the local branch can cause a `non-fast-forward` rejection.

**Note on `git commit --amend`**: amending after a push rewrites the commit (a
new hash, even with an identical message), so the next push is rejected. Amend
freely *before* pushing; afterwards you need `git push --force-with-lease` and
should expect to reconcile with the remote. See the git log/reflog if it happens
again.

## Code map

The page embeds the pure `DS991Math` core, followed by one application IIFE
containing embedded editing/rendering sources and the remaining mode logic.
Function declarations are hoisted; state initialization order still matters. Each region
is introduced by a `/* ==== SECTION ==== */` banner with a short explanation:

| region | what lives there |
|---|---|
| GENERATED MENUS | `src/menus.js`: categorized data, setup, navigation and reset confirmation |
| GENERATED MATH CORE | embedded `src/math-core.js`: polynomial roots and real nth roots |
| header comment | architecture + the **cursor model** (read this first) |
| STATE | `S`, `root`, `stack`, token factories |
| KEY LAYOUT / BUILD KEYPAD | the keyboard as data, and turning it into buttons |
| DISPLAY HELPERS | expression tree → LCD HTML, caret and slot boxes |
| NUMBER FORMAT | NORM/FIX/SCI, engineering, exact fractions |
| EDITING | caret model, movement (`moveLeft/moveRight/moveUp/moveDown`), deletion, `input*()` |
| EVALUATOR | tree → value; real and complex share one path |
| MENUS / SETTINGS / MODES | menu state machine and the calculation modes |
| BASE-N / MATRIX / VECTOR / STATISTICS | the mode-specific maths |
| RENDER | one draw function per screen |
| CLEAR / ANS | `=` , STO, CALC and numerical SOLVE |
| MODE KEY HANDLERS | editing the cell grids of the non-expression modes |
| DISPATCH | the single entry point for every key press |
| OPTN ACTIONS / PHYSICAL KEYBOARD / INIT | option menus, real keyboard, boot |

The `pos` of a cursor frame is a **digit offset**, not a token index — a token
such as `"12"` spans two caret positions. That is what makes LEFT/RIGHT move one
digit and UP/DOWN line the numerator up with the denominator.

### Exponents

A power renders through a small layout context rather than plain CSS:

```
renderNode(node, ctx)          ctx = {powerDepth, fontMode, layoutMode, rootFont}
   └── renderPow(node, ctx)
         ├── base : ctx with fontMode NORMAL
         └── renderExponent(exp, ctx)   fontMode EXPONENT, powerDepth + 1
```

`fontMode` is deliberately **not** inherited through an exponent: every level
sets `EXPONENT` again, and the size is an absolute `rootFont * 0.70` px, so
level 2, 3, 4 … are all the same size. Only `powerDepth` grows, and that is what
drives the lift (`rootFont * 0.30 * depth` px) — one constant step per level.
Sizing it in `em` would compound (70/49/34%) or shrink the step, which is what
made deep towers unreadable.

Two consequences worth remembering:

* `.exprline` must stay `overflow:visible`. A relative offset does not grow the
  line box, so `overflow:hidden` (the old value) clipped the upper levels of a
  tower right off the screen.
* the vertical position is handled by `ensureCursorVisible()`: it measures the
  caret against the LCD and offsets the whole line, clamped by
  `MAX_VERTICAL_SHIFT`, so the caret stays visible and a very deep expression
  can never be pushed completely out of view.

Keyboard shortcuts go through the same dispatcher as the on-screen keys, so a
shortcut behaves exactly like pressing the key:

| key | acts as |
|---|---|
| `0`–`9` `.` `,` | digits, decimal point |
| `+` `-` `*` | `+` `−` `×` |
| **`/`** | **fraction template** (`⌐`), *not* division |
| **`^`** | **power template** (`x^`) — the same key as the on-screen `x^` |
| `!` | reciprocal (`x⁻¹`) |
| `(` `)` | parentheses |
| `%` | Ans |
| `Enter` / `=` | `=` execute |
| `Backspace` / `Delete` | DEL |
| `Escape` | AC |
| arrow keys | the d-pad |
| **`Shift`** | no calculator action by itself; use `s` for sticky SHIFT |
| `s` `a` | SHIFT / ALPHA (sticky, they arm the next key) |
| `m` `o` `c` `x` `e` `r` | MENU, OPTN, CALC, `x`, ENG, S⇔D |

`s`/`a` arm SHIFT/ALPHA for the next calculator key. Physical Shift only changes
which character the browser produces: for example `Shift`+`6` produces `^` on a
US keyboard and inserts a power template. Shift alone does not arm sticky SHIFT.

Shortcuts match **`event.key`** (the produced character), not physical
`event.code`. Non-US layouts therefore follow their produced characters; full
physical-position support under IMEs is not implemented. Events during IME
composition are ignored. Ctrl/Alt/Meta combinations are left to the browser.

Regression suites (no third-party dependencies, Node.js 22+) — see `tools/README.md`:

```bash
node tools/run_tests.js      # run everything
```

Chrome/Chromium probes (Node.js 22+). Browsers are auto-detected on macOS,
Linux and common Windows install locations; override with `CHROME_PATH`.
They use current `--headless`, temporary profiles and random local ports.
The tools require permission to launch Chrome and listen on localhost.
Only restricted container environments should set `CHROME_NO_SANDBOX=1`.

Layout/visual debugging helpers:

```bash
tools/shot.sh out.png "2 ADD 3"        # headless screenshot, replays a key sequence
tools/shot.sh out.png "INTG 0 RIGHT 1" # (the page reads ?keys= on load)
node tools/computed.js '.key[data-key="MENU"] .sl.right'   # browser computed style
node tools/rects.js --keys "INTG XKEY" ".bigop" ".lim"     # element geometry
```

`shot.sh` exists because the Node suites check logic and markup but cannot see
layout; `computed.js` and `rects.js` take the browser's own answer for style and
geometry, which is the only reliable way to catch CSS cascade or overflow
problems (a rule can look correct in the source and still lose on specificity).

## Continuous integration

`.github/workflows/checks.yml` runs on pushes and pull requests: embedded sources /
HTML synchronization, ten regression suites, publishing guard scenarios, browser
lifecycle checks and real Chrome smoke tests at phone and desktop widths. It checks changes without
publishing the site. GitHub Actions execution is confirmed only after pushing.
